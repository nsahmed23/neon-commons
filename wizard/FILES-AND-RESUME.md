# File ownership, concurrency and selective resume

The original reference writes only a NEW staging destination. `write_project` rejects traversal, symlink ancestors, reserved Windows names and existing foreign directories. It writes all files and manifest under a sibling temporary directory, then renames the complete directory. A per-destination exclusive lock prevents cooperating sessions from racing. This is not a hardened multi-user sandbox; external actors racing filesystem checks remain a threat requiring OS permissions.

Rerun: equal desired hashes plus unchanged owned files returns unchanged. Changed input or any edited/missing owned file causes a conflict; no merge/overwrite. Unrelated user files are untouched. Proposed changed generation must use a new staging directory, show a per-file diff, then a separately designed explicit merge. Do not overwrite the existing repo merely because a wizard answer says proceed. Backups should be local/restricted and avoid retaining secrets; retention is an organization input.

Crash before rename leaves the old destination untouched and possibly a temporary folder/lock. Recovery checks process ownership and manifest before an operator removes a stale lock. Never automatically delete arbitrary temp paths or locks. Concurrent different destinations are independent; same destination fails fast. Interrupted local generation does not mean an import or cloud operation happened.

Resume contains validated decisions, saved safe stage, data/version/target fingerprints, generated-file hashes and question provenance. No credentials or persisted authorization. `invalidated` returns the earliest affected suffix: source/tenant/cloud/IDs -> inventory; provider/API/engine/ownership -> mapping; Atmos/stack/component/revision/dirty files/edited output -> generation; cohort/plan/identity -> review. Unknown changes invalidate all. `resume_validation` selects that stage; unchanged goes through explicit resume_dispatch keyed to the stored safe stage, never unconditionally to a late preview. Corrupt or unsupported saved stages go to the offline alternative. External receipts are not replay instructions.

The graph's `receipt_validation` consumes separately authenticated result evidence, not a user-authored success string. It is a contract, not an implemented attestation verifier. Any adoption claim needs baseline/ID/relationship comparison and effect evidence in the qualified environment. A no-op local mock is insufficient.
