# Opening an existing service authority

`ServiceJob`, `AdoptionJob` and the separately qualified `RecoveryPlanJob` open an existing authority through `ServicePolicy(policy_path, initialize=False)`. The constructor still validates the private paths, policy, pinned verifier, signing keys and admitted manifest list. It opens the database with SQLite `mode=ro`, `query_only=ON`, `trusted_schema=OFF` and zero timeout to validate the existing core schema. It does not create a directory/database, run DDL or silently upgrade old data. A reserved writer can remain active while status/attach reads its committed snapshot. An exclusive lock can still prevent a read; this is not a promise that every concurrent read succeeds.

The supported schema is the exact six core table declarations generated by the existing initialization and migration code, including controller columns and unique constraints. Views, generated columns, missing constraints, triggers or changed conflict/collation/check declarations are rejected. Additional typed operation tables retain their own readers and validation. This is a trusted private local SQLite authority, not protection against a hostile process that controls the same account or a tamper-evident external database.

`service_store_missing` means the existing private authority root or database was absent. `service_store_schema_required` means the database cannot establish the supported existing schema. Neither status nor attach repairs it.

An authorized maintainer must first stop controllers, preserve the authority and all job/policy/artifact bytes with the repository backup procedure, and review the exact database condition. The existing Python preparation API `ServicePolicy(policy_path)` (equivalently `initialize=True`) retains its original initialization behavior: it creates missing supported tables and adds the two legacy controller columns. Normal `prepare_job` entrypoints continue to use that API. There is no new migration CLI. A maintainer can explicitly invoke that existing API in the pinned service runtime after reviewing the backup; it grants no operation approval. It does not repair arbitrary altered constraints, unsupported schemas, missing job rows or lost evidence. Those conditions require a separately reviewed restoration/migration; do not delete the database to make an error disappear.

Shared database contexts preserve the primary error when close also fails. A secondary interruption remains visible with the primary as its cause. No retry, timeout increase, import, apply, cancellation or authority migration is introduced by reopening.

The focused local gate uses real SQLite locks, independently generated Ed25519 key material and actual text status/attach entrypoints. Its durable rows are explicit fixtures, not native execution or platform evidence. Four failures on the old public constructors, the first schema/cleanup shortcomings, and their independent before/after evidence remain preserved. Native recovery and final-package qualification are separate gates.
