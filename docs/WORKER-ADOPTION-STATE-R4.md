# Closed state-only adoption projection and broker

Staged candidate only. The state contract fills the missing existing-object import content gate; it does not grant execution, global ownership, authenticated Azure state, live service qualification or production approval. The service owner must supply the separate signed operation, same physical shared authority/reservation, sealed ownership scan admission and actual authenticated receiving-backend observations.

`NativeAdoptionStateContract` derives an exact one-resource successor from independent sealed Graph capture and known existing empty state bytes. It accepts only version4/Tofu1.13.1, original lineage/serial+1, no outputs/private/dependencies, exactly selected Settings Catalog JSON resource, native schema/identity integers0 and explicit null check-results. The original baseline may omit check-results as the retained native fixture did. Baseline bytes, strong ETag/content revision, full selected backend, source/effective-input/locks and exact captured raw preimage/reader identity are bound for the separate approval.

The first projection supports Windows10/MDM, explicit nonsecret choice-setting instances with null template references (nested choices bounded16 levels), exact service setting IDs, direct explicit assignments, supported group/exclusion/all-device/all-user targets and explicit filter fields. Unknown fields, secret settings, other types, absent/null filter substitutions and unknown metadata reject. It preserves settings/child order and raw preimage bytes, independently binds assignment IDs/source metadata even where provider state has no field, sorts provider set projections, and uses pinned Go JSON map ordering/HTML escaping and RFC3339 timestamp semantics. This bounded profile is not a claim that arbitrary Settings Catalog schemas are supported. Mapping ID37 remains `unsupported` with original blockers; complete raw collection does not promote it.

`admit(bytes)` is one-use even on failure. It validates the whole canonical successor, retains original native PUT bytes in a private exclusive/fsynced file, then performs a new actual reader capture immediately before broker dispatch. Exact raw parity is required; denied/partial/stale/changed Graph blocks state. The residual Graph-read-to-state-write race remains explicit. The broker rechecks controller/identity/lease after that read. The sealed `AdoptionStateObservation` returned by read-only `observe_successor` proves projection plus fresh Graph only; caller-supplied state/revision are not Azure authentication. All release/reconciliation authority flags remain false until a separate service proof composes actual receiving-backend evidence.

The staged broker patch accepts `adoption_contract` only as the exact new process-held class and requires the sole state-write route to use that same object and exact contract hash. Graph routes are exactly the three native policy/settings/assignments GET routes; all Graph mutations reject. `native_lock_metadata_adoption` admits observed `OperationTypeInvalid` only within this typed import lifecycle. Normal policy validation, Apply metadata, ordinary state/recovery classes and no-network worker profiles remain unchanged. A separate ordinary Plan-only policy has no state-content or Graph writes. Exact contract threading through `BrokerCredentials.check/replace` retains backend identity/target comparisons; a JSON label cannot enable import mode.

Fresh-process recovery is a separate remaining implementation. This initial contract binds its original process-held capture hash and cannot rehydrate its authority from serialized receipts or silently replace that hash with a fresh capture. An interruption may leave an empty or imported state and held native lease. Recovery must preserve original approval consumption/reservation/unknown outcome, verify original signed raw/baseline/source artifacts, rederive exact projection, independently authenticate fresh Graph/backend reads, and use a separately approved exact lease action where necessary. Current same-process projection observations do not close that requirement.
