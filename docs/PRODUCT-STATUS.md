# Product status and acceptance gates

The table below is the retained 0.3.x baseline. Current 0.5.1 scoped evidence and support boundaries are in [EPOCH-ACCEPTANCE.md](EPOCH-ACCEPTANCE.md); the accompanying exact-archive receipts and acceptance ledger determine qualification of the delivered artifact. The [0.4.0 checkpoint](COMPLETION-ACCEPTANCE.md) and [0.5.0 checkpoint](PRODUCTION-COMPLETION-ACCEPTANCE.md) are historical. Assess each prior gap against its later raw evidence, without transferring old aggregate test counts.

This is an engineering alpha for local evidence inspection and candidate authoring. Production brownfield adoption is unfinished. Release 0.3.0 adds a receipt-backed cohort workflow, target consistency inspection, conservative plan review, local operation/reconciliation simulation, executable relationship contracts, dependency integrity controls and provider source qualification. These are implemented capabilities with bounded evidence; they do not constitute an Intune production execution path. Current release test counts belong in `../RELEASE-VERIFICATION.md`. The continuing goal and gate ledger are in `ENTERPRISE-GOAL.md` and `ENTERPRISE-EXECUTION-LEDGER.md`.

“Done” means an existing Intune estate can be mapped to its actual Atmos component, backend and owner, adopted without unintended setting or targeting changes, and operated through reviewed, recoverable actions. Local fixture consistency is necessary evidence for that goal, not its acceptance criterion. The support boundary must identify resource families, exporter versions, provider/engine/Atmos versions, cloud/backend, native hosts and platforms.

## Milestones and exit criteria

| Milestone | Exit criteria | Current position |
|---|---|---|
| Local review development release | No known audit-critical local data loss/leakage or evidence bypass; commands work from clean extraction; unsupported input remains explicit | Working implementation undergoing critical audit and repair; not a production claim |
| Narrow adoption pilot | One named policy family/exporter/backend/host combination: authenticated inventory/reference/ownership, provider-valid project, protected import/plan, observed no-change adoption and failure recovery | Missing major engineering and qualification work |
| Supported production release | Declared estate coverage; production CI/auth/concurrency/reconciliation; supported native hosts/platforms; operational ownership, release integrity and behavioral acceptance | Not reached; broader scope must remain visible |

The next critical path is integration and full native qualification of the provider corrections, authenticated target/state-writer observation and a protected external action adapter. The source harness has narrowed those questions and reproduced defects; it has not qualified the published provider. Tenant access is needed for final service observations, but it does not prevent further independent engineering. CLM can help prioritize evidence review after calibration; deterministic checks remain the acceptance boundary.

No completion percentage or calendar commitment is justified by the current test count. A defensible estimate needs a named estate/support denominator and the first successful provider roundtrip, which may expose additional implementation requirements.
