# Receipt-backed guided local authoring

`wizard --guided` adds a cohort authoring journey to the existing wizard. The original single-policy wizard remains the default. Guided completion means the current local source and generated proposal still agree. It does not establish authenticated ownership, provider qualification, cohort membership, approval or adoption.

```bash
python scripts/intune-iac.py wizard --guided \
  --session /absolute/path/guided.json \
  --input /absolute/path/export.json \
  --context /absolute/path/context.json \
  --output /absolute/path/new-proposals
```

On first use all three paths are required. The bounded context must specify `authorization: emit_only`. Add `--repo` only for supported production captures with a resolvable literal repository target. The synthetic reference generator is rejected in repository mode. Optional stack/component selectors are literal target intent, not effective cloud authentication.

The wizard reads the complete export, lists observed policy UUIDs, and asks for a comma-separated selection. It supports up to 100 selected policies from an inventory of up to 1000 observed IDs. It does not filter the source capture to hide unsupported content. Existing intake, normalization, preservation and size limits still apply.

At `generate` or `partial_generate`, enter `generate` to create one proposal directory per selected UUID. Supported synthetic policies may produce active reference HCL. Blocked policies retain review artifacts and blockers. Production captures remain review-only or inactive candidates under the existing engine rules. Partial generation retains all selected policies; it does not drop the blocked policies. Nothing authenticates, initializes a provider, imports state, invokes Atmos, applies infrastructure or executes command cards.

At `adoption_preview`, review the proposal files and enter `finish` for a local handoff. `save`, EOF and Ctrl-C suspend. Resume with the same `--session` and `--guided`. A cancelled session requires `continue` before another generation attempt; saving again does not erase that requirement.

## Editing and cohorts

- `cohort ring0 UUID,UUID` records a ring and group UUID intent. Rings 0–4 are accepted; omitting UUIDs records an unspecified group set. This is handoff metadata, not a membership observation or a request to alter the captured assignments. Group existence, membership, freshness and rollout authorization remain unverified.
- `edit stack NAME` or `edit component NAME` invalidates generation and dependent milestones. Repository mode rereads and resolves the literal target again.
- `edit output /absolute/new/path` selects a fresh staging destination. Existing output is preserved.
- Editing the selected object list is available at `object_selection`. A new selection after an existing handoff uses a new guided session, preserving the prior evidence and generated files.

Cohort changes invalidate review. Changing a cohort while the saved state is `object_selection` leaves the wizard at `object_selection`. A stack change while saved at `partial_generate` returns to that partial path. Resume never treats a later changed-input boundary as proof that an earlier unfinished step occurred.

## Receipts and reconstruction

Sessions use schema `2.1.0`, distinct from the correction pack's proposed `2.0.0` decision model. This is a bounded implementation of its local progress principles, not a declaration that the entire original 32-state wizard is implemented. Existing v1 sessions are rejected explicitly by guided mode without rewriting them; resume them with the original wizard or choose a new guided session path.

The session's sibling `SESSION.evidence` directory contains an index, nine possible milestone receipts, restricted per-policy context files and fixed-runner attempt records. First use refuses a preexisting evidence directory. Receipt paths are fixed beneath that root; symlinks and parent-path aliases cannot redirect them. Receipt schema and algorithm, exact bytes, expected payload and every prior receipt hash are checked in stage order. The fixed ordered dependency chain excludes cycles and missing dependencies. Reads are bounded; receipts do not contain raw source values, tokens or approval grants.

Reconstruction reruns current source/context/repository observations and the existing mapping engine. For generated milestones it calls `engine.verify_project` for every selected UUID: source-derived preservation and expected generated bytes are checked independently of a saved manifest. It also rejects extra or missing cohort output directories. Forging a manifest hash does not make changed output valid.

The accepted completion prefix is the intersection of:

1. The saved completed prefix and saved stable-state frontier.
2. Receipts independently reconstructed from current artifacts.
3. The prefix remaining after relevant source, target, selection, output and cohort invalidation.

| Local milestone | What its receipt establishes |
|---|---|
| repository | Current bounded repository observation, or explicit context-only mode |
| source | Source/context locators and declared tenant/cloud intent |
| inventory | Current source digest, observed policy IDs and synthetic marker |
| selection | Explicit sorted selected policy UUIDs |
| ownership | An assessment whose result is **unknown**, with writer qualification false |
| mapping | Recomputed per-policy mappings and visible blocked/partial status |
| generation | Every selected output's source-derived manifest and target intent |
| validation | Independent preservation verification of the current local output |
| review | A local handoff record bound to the current outputs and cohort intent |

These local milestone names intentionally do not mean that the corresponding enterprise gates passed. `external_verified_completed` is always empty and `execution_authorized` is always false. A synthetic receipt may support the bounded synthetic authoring journey; it can never become real execution evidence. A locally writable receipt store is consistency evidence, not authentication of an operator or proof of historical activity.

## Interrupted writes and conflicts

A durable unknown-outcome marker precedes the first cohort output write. Generation uses fixed local runner actions and validates each result. A failure after output generation, including a receipt write failure, retains unknown status. Resume displays `reconciliation_required` and refuses replay. The current guided interface does not resolve that state automatically: preserve the output and attempt records for independent inspection. A new session/output is a new local proposal, not evidence that the interrupted one failed or was reconciled.

The cooperative session lock is held for the full interaction, with state reread after acquiring it. Normal suspend releases the lock; abrupt termination may leave a lock that requires inspection. Atomic per-file replacement is not a power-loss transaction for the whole evidence tree. Partial receipt updates truncate trusted progress. These controls assume a cooperative local filesystem; they do not defend against an adversary concurrently replacing filesystem components or establish a distributed lock.

## Python interfaces

- `run_guided_workflow(session_path, input_path=None, context_path=None, output_path=None, input_fn=input, output_fn=print, repo=None, stack=None, component=None)` runs the local journey.
- `run_wizard(..., guided=False)` preserves the original API and delegates when guided mode is selected.
- `reconstruct_progress(session_path)` rereads current inputs and receipts and returns `next_state`, `milestone_index`, `verified_completed`, reasons and explicit assurance limits.
- `preview_resume(session_path, changes)` evaluates bounded `cohort`, `stack` and/or `component` changes without updating persistent session/evidence/output files. The existing path-based engine uses private temporary context files that are removed after inspection.

Live prerequisites remain: independently authenticated identity and writer ownership, effective backend, provider/service qualification, a protected executor, authenticated approval delivery, actual cohort membership and reconciliation adapters, native hosts and an authorized pilot. The local handoff deliberately cannot skip these prerequisites or mark them complete.
