# Bounded native Windows storage continuation

The current native Windows private Workbench store is **UNSUPPORTED**. This is an implementation gap, independently of missing host qualification. The first useful native implementation can be a private inspection/history client over the existing SQLite store. It need not port the Linux protected execution worker or weaken that worker's network boundary. This document is a code-derived implementation recommendation, not approval of a native profile or proof that an adapter exists.

R4 continuation now includes an inactive [read-only SQLite snapshot component](WINDOWS-SQLITE-COMPONENT-R4.md) over pinned native directory/file handles. It does not enable this Workbench client or implement the write, sidecar-creation, recovery, backup or migration seam below. Its local contracts and executable native procedure are separate from absent Windows host qualification.

The later [inactive Workbench storage adapter](WINDOWS-WORKBENCH-ADAPTER-R4.md) implements that storage seam and portable schema/query reuse for component qualification. The application host gate stays unsupported while native evidence, readers and terminal dependencies remain incomplete. The implementation map below records the original gap; the linked continuation describes its bounded implementation and unresolved native gates.

## Smallest safe implementation sequence

1. Extract only the immutable observation contract and move synthetic/observer imports to their actual routes. Keep all public result shapes, database schema, field validation and Linux security behavior. Verify original Linux store/collector and invalid-field controls; an import-only success is not native storage evidence.
2. Introduce a small store filesystem interface: validate/pin private root; create/open an exclusive private file; validate root/file/sidecar identity; flush committed bytes; publish a new backup without replacement; close retained handles. The existing POSIX implementation remains the default for its existing profile. SQLite schema, queries, transaction boundaries and independent history assertions remain unchanged.
3. Implement a separate native Windows adapter over the actual system APIs. Admit only the declared local fixed-volume filesystem/architecture profile; reject UNC, network, device and ambiguous path namespaces, alternate streams, reserved names, trailing-dot/space aliases and every unhandled security descriptor/reparse case. Native support must be explicitly selected from verified capability discovery, never reached by dropping a failed POSIX check.
4. Qualify native storage security and concurrency first. Then run actual init, observation publication/import where its reader is implemented, inspection, history, backup, migration, restore and text detach/reopen. Keep Linux observer and worker gates intact. Add the remaining native reader, maintenance and visual capabilities separately with their own evidence.

A safe adapter must identify the current token SID, validate ownership and a restrictive non-NULL DACL, and reject broad or unrecognized access rather than relying on `chmod` or `st_uid`. The exact allowed privileged principals and inherited ACE policy require review. Preserve and validate file IDs, volume identity, file type and link count. Ancestors and the private root must be validated against reparse traversal and retained so pathname substitution cannot change what SQLite opens. A final-component `FILE_FLAG_OPEN_REPARSE_POINT` alone does not validate all ancestors. Do not obtain native support by invoking or parsing `icacls`, PowerShell text or an ambient command.

CPython `sqlite3` opens names using its native VFS; it does not accept an already validated arbitrary Windows file handle. The design must therefore bind and hold the verified private directory namespace while SQLite opens the DB and sidecars, and qualify that binding under rename/reparse/race attempts. A private DACL may establish the same cooperative-account boundary as the existing POSIX store; it does not isolate against a hostile process running under the same account. Any stronger claim needs a separate security boundary.

Use a qualified native durability protocol, with retained intent/recovery records and no successful durable acknowledgement after a flush/publication failure. `FlushFileBuffers`, rename flags or a successful SQLite commit alone are not proof of namespace durability across power loss. An uncertain commit must remain observable and recoverable; testing cooperative restart is a narrower result. New native journal formats need versioned migration and restoration tests before release.

`LockFileEx` may be needed for later synthetic service, approval or scheduling adapters. It is not a reason to add a second ad hoc lock around existing SQLite transactions or to substitute a no-op `fcntl` shim. Windows process/job containment, secret delivery and native console restoration are separate follow-on implementations.

## Independent acceptance and owner decisions

The native adapter requires actual Windows evidence for SID/DACL/NULL-DACL and inherited ACE controls; directory/file reparse and hard-link denial; immutable handle/volume binding under rename attempts; private DB sidecars; two-process SQLite contention; interrupted acquisition, transaction, backup and migration; failed flush/publication; exact backup/restoration bytes and tenant isolation; and every supported filename/argument shape. Assert no writes outside the disposable root and retain failed attempts. Mock API responses only qualify the adapter's local contract logic.

Workbench host-adapter maintainers own implementation. The organization's Windows endpoint/runner owner supplies the authorized disposable native host, actual filesystem and pinned CPython/shell/terminal versions. AppSec reviews ACL, handle, same-account and durability boundaries. The accountable release owner chooses the pilot profile and dispositions remaining risks. No such approval is recorded here.

The existing `scripts/qualify-windows-workbench.py --help` exposes the exact package/tool-pin inputs. It now reads the package's doctor capability contract before store probes. For the current native Windows implementation, the expected result is structured unsupported rejection without a created store. Those negative controls leave native functional qualification blocked. Once the reviewed adapter exists, the same procedure requires functional success and independent SQLite assertions; mintty/visual, service/backend/CI, device and production approval remain separate gates.
