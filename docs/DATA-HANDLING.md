# Data handling in the local development build

The CLI processes the input files and repository paths you select. Generated artifacts, graph files, sessions, locks and attempt receipts are local files. These can contain tenant and policy identifiers, accepted setting values, repository paths and configuration provenance. Treat the working directory and generated artifacts according to the sensitivity of your source data. Public repository inspection omits effective variable values; this is not a guarantee that user-chosen names or paths contain no secrets.

Unsupported raw fields remain in the original input. Review outputs use opaque source references and blocking reasons. Production accounting 1.1.0 suppresses per-field digests for restricted or loss-blocking values and all containers; only already-visible mapped scalars receive value hashes. This prevents the demonstrated independent dictionary attack against a short restricted value. Whole-source digests remain equality evidence and can reveal guesses if the rest of a source is known; hashing does not anonymize secrets. This restriction does not anonymize supported settings or make a captured tenant export public data.

New capture and generated-project directories use POSIX creation mode 0700, with files 0600, including nested review files and ownership manifests. Existing outputs are verified without silently changing user permissions. Host ACLs, inherited filesystem rules, backups and copies remain outside these POSIX mode checks. Native Windows ACL qualification remains open.

Three optional commands make network requests. `capture` sends GET requests to the documented public Microsoft Graph routes using the token from the explicitly selected environment variable. `target collect` makes three fixed TLS GETs to public Graph and Azure management using separately selected token environment variables. It checks organization, subscription and storage-account facts; it neither reads the state blob nor authenticates the claimed principal, federation, writer or approver. Its returned report cannot be reused as execution authority. `judge` sends the supplied claim and evidence to the configured CLM endpoint. Remote judge use requires explicit configuration; the service operator receives the submitted content. Pinning local model/tokenizer metadata does not authenticate a remote service's running model. The MCP interface exposes local operations, without capture, target collection or judge tools.

The runtime has no automatic dependency installation, model download, host registration or deployment step. Preparing the Python environment, running a host or enabling an external service has its own data handling outside this local package. This document describes observed code behavior; it is not a published service privacy policy or terms of service.

The source release builder includes only files named in `release-source-files.txt`. Maintainers must review additions and artifact contents before adding them. Unlisted local captures, state and environment files are excluded. The inventory is not an automatic secret scanner. Builds require a fresh output destination and preserve existing release files. Both archives use one source-byte snapshot. Building releases requires POSIX directory-descriptor/no-follow support to reject swapped symlink members or parents; this release-tool requirement does not change the plugin runtime's platform boundary. Maintainers must keep the checkout quiescent: the snapshot is consistent between archives but is not an authenticated or transactional snapshot of an actively edited repository.
