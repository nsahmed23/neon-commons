# Stopped adoption Plan lease recovery

Two closed historical phases are supported: the original adoption's initial verification Plan, and a separately approved recovery Plan. A process-held `InitialVerificationPhase` or `RecoveryPlanPhase` binds the exact registered row, operation and manifest, original adoption consumption and ownership, stopped host receipt, actual selected broker journal, and original import state-write evidence. Imported JSON does not mint a selector, receiving identity, recovery observation, release capability or reconciliation result.

`stopped_initial_verification(AdoptionJob)` selects only `verification-host-run` and `verification-broker.sqlite3`. `stopped_recovery_plan(RecoveryPlanJob)` selects only that Plan job's own `host-run` and `broker.sqlite3`, with its own consumed approval. The original import's lease journal cannot stand in for either Plan. Original import dispatch and outcome, every failed Plan outcome, and scope reservation remain unchanged during lease recovery.

`worker_adoption_plan_recovery.laboratory_context(...)` or the distinct `live_context(...)` requires the sealed phase, freshly authenticated backend identity/credential, declared storage, exact original baseline/source/capture, and freshly authenticated Graph reader. The laboratory adapter is a nonforwarding local TLS profile. Only the exact original adopted successor state, complete unchanged Graph, exact current lease GUID and `OperationTypePlan` metadata are admitted. State PUT and Graph mutation routes are forbidden. Neither baseline state nor a caller-supplied new state revision is a recovery override.

Call `context.observe(new_private_directory)` then `prepare(observation, operation_id=NEW_UUID, expires_at=...)`. Review the complete immutable manifest and receiving observations. A separate external policy and newly signed `adoption-plan-native-lease-recovery-approval:v1` domain (ending in an actual NUL byte) must admit this exact manifest. Never reuse import, apply or original-import lease-release approval. `execute()` durably consumes the new approval and reserves `native_lease_recoveries` by the selected Plan operation ID in the original common authority before one exact Blob lease release. The call rechecks original ownership, stopped phase, fresh receiving state/ETag/GUID, expiry, and absence of a competing prepared or active Plan under the transaction and immediately before dispatch. This is not force-unlock, lease break, metadata clear, import replay or ownership release.

After timeout, cancellation or recording failure, preserve the consumed approval, unknown outcome and original reservations. `observe_uncertain()` performs fresh read-only receiving verification; never retry the release. `completion()` requires fresh process-held context and exact state/Graph evidence. A normal later Plan may clear retained Terraform lock metadata and change ETag without changing state bytes; completion records both ETags and leaves attribution unestablished. Release-only completion reports backend readiness false and ownership release unauthorized. A separately reviewed successor Plan is handled by the versioned service bridge; an old failed Plan is never rerun under its old approval.

Historical phase inspection is read-only even after its dispatch policy expires. The reader checks exact registered time bounds and original policy hashes. A disposable local copy is used only for schema validation; the original expired policy remains byte-identical and rejected by the dispatch validator. Historical completion remains readable after a new successor is registered. The separate release dispatch fence rejects that competing prepared/active successor.

Local checks: `python -B -m unittest -v plugin_tests.test_worker_adoption_plan_recovery_r4` uses real signature verification, exact domain and hostile-response controls without an external fixture dependency. The external `test_plan_phase_r4.py` exercises actual public constructors, shared SQLite and read-only broker journals with explicitly modeled stopped-host rows; this is not native execution proof. Receipts record those scopes separately. Existing before failures for historical-successor coupling and expired-policy inspection remain preserved.

Native procedure: create a NEW isolated authorized adoption; interrupt only after the selected initial Plan has acquired its lease; retain original and selected phase receipts/journal and stop the controller/container. Reopen the exact operation under the same authority, construct fresh typed receiving observations, separately review/sign exact release, dispatch once, independently read back, then authorize a NEW Plan-only successor and inspect native no-change output. Repeat on a separately created recovery Plan interrupted after lease acquisition, preserving each ancestor and new approval. Negative controls require wrong phase, lease, state, identity, active controller, missing/foreign scope, spent approval, expiry, competing prepared Plan, lost response and uncertain recording. No task here grants real tenant or release authorization. Actual Azure conditional-release behavior, native platform qualification and accountable organizational approval remain separate external gates.
