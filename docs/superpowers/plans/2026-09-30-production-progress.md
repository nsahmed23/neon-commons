# Repository-aware Intune IaC implementation plan

Goal: remove work that unnecessarily depended on a tenant or a prepared context file, and deliver a verified next development release.

Architecture: retain the fixed local action runner and independent preservation checks. Add a bounded, effect-free Atmos resolver, a versioned production capture projection, and a repository-first terminal workflow. Native provider and cloud execution remain separate qualification gates.

Spec: the user's Appendix B corrections, repository semantic requirements, and instruction to build and execute the plan. The existing runtime contracts remain binding unless explicitly versioned.

Tech stack: Python 3.12, pinned PyYAML/jsonschema/python-hcl2, stdio MCP, local JSON receipts, existing OpenTofu/Atmos reference modules.

## Constraints and review focus

- Never relabel a production capture as synthetic or infer missing assignments as empty.
- Preserve setting IDs, exclusions, filters, and source field lineage; unsupported content stays in restricted input.
- Resolve only a documented literal Atmos subset, using inspected v1.199.0 source. Dynamic constructs remain blocked. Configuration inheritance and component implementation are distinct relationships.
- Discovery and graph outputs must not reveal arbitrary variable, backend, environment, or provider values.
- Repository changes invalidate saved selection/generation evidence. A stored hash is not independent proof.
- Candidate provider configuration is inactive until separately qualified. Tests and generated bytes cannot prove live no-change adoption.
- Keep filesystem boundaries, ownership conflicts, action receipts, and command allowlists intact.

## Tasks

1. Implement repository discovery and literal Atmos resolution.
   - New `repository.py`: `discover_repository(root)` and `resolve_component(root, stack, component)`.
   - Tests: import ordering, map overrides, list replacement, inheritance order, cycles, missing imports, unsupported YAML/templates, containment, and fingerprint changes.
   - Resolution includes source hashes and per-field origins; discovery returns selectable physical stack/component identities.
2. Implement a real-capture mapping path.
   - Separate production projection/oracle; dispatch only the plugin's known capture exporter.
   - Preserve observations and proposed configuration separately; generate inactive candidate files for the bounded supported shape.
   - Tests: realistic metadata, opaque setting IDs, assignment completeness, external references, policy-set ownership, unsupported-value leakage, and independent mutation rejection.
3. Implement repository-first wizard and semantic graph integration.
   - Select discovered stack/component and captured policy; create an owned context file.
   - Re-resolve on resume and before finish; invalidate output when repository evidence changes.
   - Graph distinguishes effective structural resolution from declarations and represents implementation/dependency provenance without secret values.
4. Integrate public interfaces and local action contracts.
   - CLI `repository inspect` / `repository resolve`; wizard repository flags; read-only MCP tools and fixed runner actions.
   - Test schema rejection, read-only behavior, byte binding, and CLI/MCP routing.
5. Review, verify, and release.
   - Fresh independent review of new code and boundaries; repair substantive findings with regression tests.
   - Run all existing and new tests, actual CLI journeys and terminal qualification, then clean-extraction tests.
   - Update capability docs/version, run Plugin Eval static analysis, build versioned runtime/source archives, and save artifacts.
